## Part 1: Optimizer roster change

**Drop:** Lion, SGD, AdaHessian
**Keep:** SOAP, AdamW
**Add:** Muon

**Rationale (put a short version of this in code comments/README, not just this prompt):**
The project's goal is real-world digit-reading accuracy, not just test-set accuracy or research novelty. Lion showed a reproducible ~20-point real-world accuracy gap at 128×128 in prior validation (v1), independently confirmed on a second machine — a known, unresolved failure mode. SGD was consistently the weakest performer across prior resolutions. AdaHessian was already dropped from the project earlier (excessive compute cost — 24+ hours per run at 128×128 with the wall-clock limit removed) and should not reappear anywhere in the restructured codebase; remove any remaining AdaHessian scripts, references, or dependencies entirely. Since the current priority is a trustworthy ensemble rather than documenting an interesting failure case, Lion and SGD are cut for the same underlying reason. Muon is added based on current (2025-2026) independent benchmarks showing it reliably outperforms AdamW-class optimizers across multiple domains, at a lower per-step compute cost than SOAP.

**Note:** Muon needs a secondary/fallback optimizer for non-2D parameters (biases, norm layers, embeddings) since it's designed around 2D weight matrices. Use AdamW as that fallback within the Muon training script, consistent with common Muon implementations.

**Resolution tiers differ by dataset source:**
- MNIST, EMNIST Digits, SVHN, ARDIS: 28×28 → 32×32 → 64×64 → 128×128
- USPS: 16×16 → 32×32 → 64×64 → 128×128 (starts at its own native 16×16, skips the 28×28 tier — 28×28 isn't native or meaningfully closer to native for USPS, so it sits that round out)

Both ladders converge at 32×32, 64×64, and 128×128 — every model at those three tiers trains on the full merged dataset as before. Only the bottom tier (28×28 vs 16×16) differs by source. This must be handled in the shared dataset loading module (Part 2) — the loader needs to know, per resolution tier, which sources are included, since USPS is absent from the 28×28 tier and everyone else is absent from the 16×16 tier.

**Resulting model matrix:** 3 optimizers (SOAP, AdamW, Muon) × 4 resolution tiers = 12 digit models total, where "4 resolution tiers" means the per-source ladders above, not one uniform resolution list.

## Part 3: Router/classifier model rewrite

**Important — the existing model is not what this section originally assumed.** The v2 files include `mnist_digit_gate.py` (referenced from `ocr_pipeline_mnist.py`), which is a **binary digit / not-digit gate** with three inference-time verdicts (`digit`, `not-digit`, `unsure`, via a confidence band `GATE_UNSURE_LOW`/`GATE_UNSURE_HIGH` around a single `P(digit)` output) — not a 4-class digit/UC/LC/unknown classifier. This is the closest existing artifact to "the router," but building the digit/UC/LC/?? classifier described below is an expansion of its scope (2-class → 4-class), not a rename or light rewrite. Confirm this understanding against the actual repo state before proceeding, since if a more advanced router already exists elsewhere it supersedes this description.

**Output marker collision — resolved decision, implement exactly this:** `ocr_pipeline_mnist.py` already uses `??` for two distinct existing cases (ensemble couldn't agree on a digit — shown as "✗ split"; gate confidently said not-digit — shown as "✗ gate", tracked internally as the `GATE-NOT-DIGIT` agreement state) and a separate `[NON-DIGIT?]` marker for low ensemble confidence (`NON-DIGIT` state). Do not add a third meaning to `??`. Instead:
  - The router's genuinely-unclassifiable verdict gets its own distinct marker: `[UNK]`, with its own agreement-state constant (e.g. `ROUTER-UNKNOWN`), parallel to how `GATE-NOT-DIGIT` is already threaded through the codebase.
  - `??` keeps its existing two meanings unchanged (ensemble split / gate not-digit), with existing "✗ split"/"✗ gate" flags unchanged.
  - `[NON-DIGIT?]` keeps its existing meaning unchanged.
  - `[UNK]` needs the same downstream treatment `GATE-NOT-DIGIT` already gets: excluded from accuracy scoring (with its own warn line, e.g. "N character(s) flagged unknown by the router — excluded from accuracy count"), its own count in PER-MODEL SUMMARY-style output, and its own flag in CHARACTER DETAIL (e.g. "✗ router").
  - Update the module docstring's "Output markers" section in `ocr_pipeline_mnist.py` to document `[UNK]` alongside the existing `??` and `[NON-DIGIT?]` entries.
  - This is a decision already made — do not re-derive or ask about it; implement as specified.

**Wiring impact — the gate is not a bolt-on, it's threaded through scoring:** `GATE-NOT-DIGIT` is not just a display label. It's a first-class agreement/verdict state used in: ensemble voting output, the CHARACTER DETAIL per-model breakdown, PER-MODEL SUMMARY (`[G?]` marker), and accuracy scoring (explicitly excluded from the correct/total count with its own warn line). **Resolved decision, implement exactly this: the router fully replaces the gate.** Remove `mnist_digit_gate.py`'s binary gate entirely — do not keep it running alongside the router. The router's 3-class output already subsumes what the binary gate did (a gate "not-digit" call is equivalent to the router saying UC/LC/[UNK] instead of digit), so running both would mean two overlapping uncertainty systems doing redundant work with no real benefit. Concretely: remove `--gate-model`/`--gate-unsure-band` CLI args and all gate-loading code paths from `ocr_pipeline_mnist.py`; replace every `GATE-NOT-DIGIT`/`gate_verdict`/`gate_prob` call site (ensemble voting, CHARACTER DETAIL, PER-MODEL SUMMARY's `[G?]` marker, accuracy scoring's gate-exclusion count) with the equivalent `ROUTER-UNKNOWN`/`[UNK]` handling already specified above. Search the full file for every reference to `GATE-NOT-DIGIT`, `gate_verdict`, `gate_prob`, and `--gate-model` and replace each one — do not leave any gate-era code path in place. Document this replacement (not coexistence) decision in the v3 changelog with the reasoning above.

**Box detection is currently tuned for digit shapes specifically:** `get_boxes()`'s multi-scale size windows, aspect-ratio filters, and the character-splitting logic (gap detection, distance-transform fallback for touching characters) were tuned against digit test images. Letters — especially lowercase letters with ascenders/descenders (b, d, g, p, q, y) or narrow letters (i, l) — may have different natural aspect ratios and heights than digits, and could be rejected by the current height/aspect filters before ever reaching the router for classification. Verify the existing `SIZE_WINDOWS` and aspect-ratio bounds (`0.1 < aspect < 10.0`) actually admit realistic letter bounding boxes, particularly ascender/descender letters. If they don't, widen the bounds as needed and document the change and reasoning in the v3 changelog — resolve this yourself rather than leaving box detection unchanged on the assumption it's fine.

1. **Optimizer:** switch from AdaBelief (the gate's current optimizer, per its existing `scaled_learning_rate()`/`REFERENCE_BATCH_SIZE`/warmup machinery tuned specifically for AdaBelief's small-batch behavior — see the v2 changelog's 2026-07-27 entry) to Ranger (RAdam + Lookahead). Ranger's batch-size/LR-scaling characteristics differ from AdaBelief's — do not assume the existing square-root LR scaling, `REFERENCE_BATCH_SIZE=256`, or warmup-length derivation carry over unchanged. Re-derive or re-tune these for Ranger specifically, and document the reasoning in the new v3 changelog the same way the v2 AdaBelief fix did (verified before changing, mechanism of the fix, what was checked).
2. **Output classes:** the router must classify each input box into one of four categories and this is the required output format:
   - Digit → pass to digit ensemble as normal
   - Uppercase letter → output `UC` (no uppercase specialist model exists yet — this is a terminal label for now, not a further routing step)
   - Lowercase letter → output `LC` (same — no lowercase specialist model exists yet)
   - Unclassifiable/unknown → output `[UNK]` (see the resolved confidence-threshold decision below — this is not a trained fourth class, the router's output head is 3-class digit/UC/LC)

**Training data:** the existing `supplementary_data.py` already contains letter dataset support (EMNIST Balanced, Kaggle A-Z, Chars74K, PG-HWLD) that is currently disabled (`use_balanced`, `use_kaggle`, `use_chars_hnd`, `use_chars_img`, `use_pghwld` all False) for the digits-only project. For the router's UC/LC classification training, re-enable EMNIST Balanced as the primary letter source (it's already fully implemented and wired in) — it provides both uppercase and lowercase classes needed to teach the router the UC/LC distinction. EMNIST Balanced already downloads to the same `DATA_DIR` as the other torchvision-managed sources (EMNIST Digits, MNIST, USPS, SVHN) per the existing `supplementary_data.py` structure — no new path constant is needed for it, it reuses `DATA_DIR` like its digit-only sibling. Kaggle A-Z/Chars74K/PG-HWLD may optionally be added as supplementary letter sources at your discretion, but EMNIST Balanced alone is sufficient to start. The router's training set is therefore: EMNIST Balanced (letters, mapped down to just uppercase-vs-lowercase rather than full 62-class byclass) plus the same merged digit sources already used for the digit ensemble (MNIST/EMNIST Digits/USPS/SVHN/ARDIS, mapped to a single "digit" class rather than individual 0-9 labels) — the router only needs to distinguish digit vs. UC vs. LC vs. unclassifiable, not identify specific characters.

**Unclassifiable (`??`/`[UNK]`) handling — resolved decision, implement exactly this:** confidence-threshold approach, not a dedicated reject class. The router's output head is 3-class (digit / UC / LC) — no fourth "reject" training class. At inference, if the router's top-class confidence falls below a threshold (new constant, e.g. `ROUTER_UNSURE_FLOOR`, tunable via CLI like the existing `--gate-unsure-band`/`--non-digit-floor` pattern), output `[UNK]` instead of the top class. Rationale: this requires no new negative-example training data (which doesn't exist anywhere in the codebase currently) and is consistent with the existing gate's own confidence-band approach (`GATE_UNSURE_LOW`/`GATE_UNSURE_HIGH`) rather than introducing a second, different uncertainty-handling mechanism. Document this choice in the v3 changelog the same way other resolved decisions are documented (why, and what was considered and not chosen).

**Locating the existing router:** the closest existing implementation is `mnist_digit_gate.py` in the v2 repo (the binary gate, not yet the 4-class router). Read the actual file directly from the repo rather than relying only on what's been discussed in this conversation, since the real file may contain details beyond what was excerpted here. If a more advanced router implementation already exists elsewhere in the v2 repo, use that as the starting point instead of `mnist_digit_gate.py` — proceed with whichever is the more complete existing base, and note the substitution in the v3 changelog rather than pausing to ask.

**Resolution:** train the router matching the same per-source resolution ladders as the digit ensemble (see Part 1's resolution tier breakdown — MNIST/EMNIST/SVHN/ARDIS at 28/32/64/128, USPS at 16/32/64/128). Rationale: the router has to classify each box before handoff to a specialist model, at whatever resolution the pipeline is currently operating at. A single fixed-resolution router would force an extra resize/interpolation step before classification (adding distortion) or be evaluated at a resolution it wasn't trained on — the same test/real-world mismatch this project's methodology is built to avoid. Matching tiers keeps the pipeline consistent and lets router accuracy be honestly evaluated per-resolution like everything else.

**Pipeline integration:** the router should run first in the full pipeline — read the input document/test image, detect and verify every box, classify each box (digit / UC / LC / [UNK]), then hand digit-classified boxes to the appropriate optimizer models in the digit ensemble for reading. Final pipeline output should show best-guess results per box: actual digit predictions where read, `UC`/`LC` for letters (no further reading since no letter specialist models exist yet), and `[UNK]` where the router couldn't classify the box at all.

**Scope note — future letter-specialist models:** the project's longer-term plan (lowercase-only and uppercase-only specialist model sets, reading actual letter identity beyond just case) is not yet planned out or fleshed out — it's a future phase, not part of this restructure. Do not build speculative infrastructure for it now (no placeholder specialist model hooks, no over-engineered box/crop-preservation scheme anticipating a future handoff) — just get UC/LC/digit/[UNK] classification and display working correctly for this phase. Keep the router's design simple and correct for what it needs to do today.

**Real-world validation is out of scope for this task.** Once training completes, do not attempt to run or simulate real-world validation (phone-photo testing, ground-truth accuracy scoring against the new roster) — the user will handle that separately once models are trained, uploading their own test data. ## File naming convention

All digit model training scripts, checkpoints, and exported model files must follow this pattern:

`v3_mnist_digit_{optimizer}_{resolution}`

Example digit model filenames: `v3_mnist_digit_soap_28.py`, `v3_mnist_digit_adamw_32.py`, `v3_mnist_digit_muon_64.py`, `v3_mnist_digit_soap_128.py`, etc. — one file per optimizer/resolution combination (12 total), applying to training scripts, checkpoint files, and exported ONNX files alike.

The router/classifier model isn't a digit model, so it follows the same scheme with `router` in place of `digit`: `v3_mnist_router_ranger_{resolution}`, e.g. `v3_mnist_router_ranger_28.py`, `v3_mnist_router_ranger_128.py`, etc.

Remember USPS's resolution ladder differs (16/32/64/128, not 28/32/64/128) — this affects which resolution-tagged files exist for the 28 vs 16 tier, per the resolution breakdown above, not the naming pattern itself.

Every v3 file is built fresh under this naming convention, adapted from its v2 counterpart (e.g. `v3_mnist_digit_soap_64.py` is adapted from v2's `mnist_soap_64.py`; `v3_mnist_router_ranger_64.py` is adapted from v2's `mnist_digit_gate.py`). Note: `ocr_pipeline_mnist.py` (rebuilt from the v2 version, per Part 2/3 above) references model files by path/pattern (`--gate-model`, `--models`, `--model-dir`, and the `short_model_name()` regex matching `v1_{optimizer}_{res}_{res}` and `{optimizer}_{res}` patterns) — update these references and the regex pattern in the rebuilt version to recognize the new `v3_mnist_digit_*` / `v3_mnist_router_*` naming, since the pipeline will fail to parse model names correctly otherwise.
